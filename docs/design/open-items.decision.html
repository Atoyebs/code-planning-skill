Open items from the handoff: decisions

Status: chosen during the first build (2026-11-13). All are adjustable; none was explicitly confirmed by the owner.

The build handoff (feature-planning-skill-handoff.md) left several items open. This page records what was built for each, what else was considered, and why.

ItemChoiceOptions consideredWhy, and the trade-off
Diagram format A small boxes-and-arrows format drawn by the dashboard itself. Two types: graph (the agent places each box on a grid by column and row) and sequence (actors and ordered messages). Mermaid (the handoff's suggested default); the simple format (its stated fallback). Mermaid would add roughly 3 MB to every plan file and is hard to style to match the design. The simple format is about 150 lines, matches the artboard exactly and works offline. Trade-off: no automatic layout, so the agent must pick sensible grid positions, and entity-relationship diagrams are plain boxes rather than tables with fields. Mermaid can be added later as a third source type without changing existing plans.
Saving state from a static page Every change is kept in the browser (localStorage). "Save for agent" writes plan.state.json directly where the browser allows it (Chrome, Edge) and downloads it otherwise (Firefox, Safari). Direct save; download; a tiny local server. No server to start or stop, and nothing is lost on reload. Trade-off: after a reload the developer clicks Save once more to reconnect the file, and Firefox and Safari users move the downloaded file by hand.
Third file name and scope plan.state.json holding notes, decision picks and ticks. plan.comments.json holding notes only. Everything the developer does lives in one file the agent never rewrites wholesale, so it cannot collide with agent edits to plan.json.
Viewer framework Plain TypeScript. The page is rebuilt from the data after each click. Preact, Svelte. The dashboard is small and its state is one object, so a framework would add a dependency without removing much code.
Validation One Zod schema (src/schema.ts) with the word budgets built in, bundled into the command-line tool. TypeScript types plus a generated JSON Schema file. One source of truth instead of two files to keep in step, and budgets and cross-links (every criterion traced to a step and a test) are checked in the same pass. Trade-off: there is no standalone JSON Schema file for other tools. Zod can generate one if it is ever needed.
Notes UI Every item has a small note button showing its open-note count. It expands a panel under the item with open notes, resolved notes tucked away, and a box with two buttons: "Add for agent" and "Add note to self". An "open notes" button in the header lists every open note. Not designed in the artboard. Built in the artboard's style from the behaviour the handoff agreed.
Sub-agent files Briefs are plain markdown files inside the skill (agents/*.md) that the main agent hands to whatever sub-agent it has. Claude Code custom agent definitions. Works the same whether the skill is installed as a plugin, copied by hand, or used by another agent.
Repo layout Source at the repo root; the installable skill in plugin/skills/feature-plan/ with its build output committed. Viewer source inside the skill folder (the handoff's sketch). People who install the skill get only what it needs to run, and need Node but no install or build.
Other agents Not answered. Nothing in the files is Claude-specific except the optional allowed-tools line in SKILL.md. Any agent that can read files and run Node should work; only Claude Code has been considered so far.
